# Phase 4 synthetic corpus inventory

Corpus version: **1** (`tests/support/parse_corpus.py`, `CORPUS_VERSION`). Pinned manifest:
`tests/support/parse_corpus_manifest.json` (case, category, MIME, expected status and class, size, SHA-256).

Every file is generated in code. No binary fixture is checked in, and no client document is used. The
generators are deterministic: DOCX zip entries and core properties carry a fixed timestamp, and the PDFs are
written byte for byte. `tests/unit/test_parse_corpus_manifest.py` fails if any generated byte changes, so a
change in an expected result cannot happen silently. A change requires a new `CORPUS_VERSION`, a regenerated
manifest, and an update to this inventory.

## Categories

- **valid**: well-formed TXT, PDF and DOCX that must parse. The DOCX has a table, so it also tests cell locators.
- **invalid**: structurally broken or non-UTF-8 input that must fail with a stable class.
- **partial**: an image-only PDF page inside a readable document, and an email with an HTML-only body. Each
  must be `partial` with a named flagged region.
- **oversized**: input over the 25 MiB limit, and a ZIP whose inflate ratio is over 100:1.
- **restricted**: an encrypted PDF (refused). TXT and DOCX with restricted classification parse normally;
  classification governs reads, not parsing.
- **quarantined**: content whose scan status is quarantined. The parser must never run on it. The corpus row
  records the expectation; `test_a_quarantined_version_is_refused_by_the_parser_and_writes_nothing` exercises it
  against real PostgreSQL.

The corpus holds 17 cases in six categories: 14 parse cases and 3 quarantine rows. The plan's sprint text
lists six categories (valid, invalid, partial, oversized, restricted, quarantined) across TXT, PDF and DOCX; the
corpus covers those six. No separate sixteen-category list is recorded in the plan, so WDS should confirm
whether one exists.

## How the corpus is used

- `tests/unit/test_parse_isolation.py`: every parseable case runs through the isolated child and the in-process
  parser. Results must match exactly (status, flagged regions, locators and text), and failures must match in
  class.
- `tests/integration/test_parse_reparse.py` and `test_parse_demonstration.py`: committed and rolled-back runs
  use the same bytes through the upload service and the database.
- Oversized cases are refused before any parser runs, so they are tested through the size check.
