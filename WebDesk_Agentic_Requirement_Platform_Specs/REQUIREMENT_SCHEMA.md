# Canonical Requirement and Scope Data Schema

- **Status:** Working draft for independent re-review; NOT implementation-approved
- **Version:** 0.3.10-foundation-gate1-review
- **Last updated:** 2026-10-16
- **Authority:** Canonical entity names, enums, lifecycle and traceability contracts

## 1. Design principles

1. Preserve client wording separately from normalized interpretation.
2. Every client-derived requirement has stable provenance.
3. Distinguish client request, system inference, and specialist recommendation.
4. Use explicit enums; do not encode state in free-form prose.
5. Store revisions and decisions, not just the latest overwritten value.
6. Use structured records suitable for Pydantic and PostgreSQL.
7. Keep estimates and feasibility provisional until supported and reviewed.

- `RequirementType`: `functional`, `integration`, `data`, `security`, `performance`, `availability`, `operational`, `compliance`, `ux`, `migration`, `reporting`, `constraint`, `business_rule`, `unknown`
- `Priority`: `critical`, `high`, `medium`, `low`, `unassigned`
- `RequirementStatus`: `captured`, `normalized`, `needs_clarification`, `under_analysis`, `solution_proposed`, `verified`, `accepted_for_scope`, `deferred`, `rejected`, `blocked`, `superseded`
- `EvidenceStatus`: `verified`, `partially_verified`, `unverified`, `conflicting`, `not_applicable`
- `FeasibilityStatus`: `feasible`, `feasible_with_conditions`, `not_feasible`, `unknown`, `conflicting`
- `ConfidenceBand`: `high`, `medium`, `low`, `not_assessed`
- `QuestionStatus`: `open`, `answered`, `waived_by_authorized_human`, `superseded`
- `FindingSeverity`: `critical`, `major`, `minor`, `informational`
- `FindingStatus`: `open`, `in_progress`, `resolved`, `accepted_risk`, `not_applicable`
- `ReviewOutcome`: `blocked`, `changes_required`, `pass_with_conditions`, `pass`

## 3. Stable identifiers

Use readable prefixed IDs or UUIDs with an immutable external display ID. Examples: `PRJ-...`, `SRC-...`, `REQ-...`, `EVD-...`, `Q-...`, `SOL-...`, `SCOPE-...`, `RISK-...`, `ASM-...`, `EXC-...`, `REV-...`, `FIND-...`, `RUN-...`, `DEC-...`, `SOW-...`.

IDs are generated by application code, not requested from an LLM. Do not reuse IDs. A split requirement creates child/new IDs with `derived_from` links; a merged record preserves links to all source requirements.

## 3.1 Foundation authorization, classification and deletion contracts

### Foundation permissions (F-1; WDS-approved)

The canonical Foundation action×role matrix, resource authorization and separation of duties are defined only in `GOVERNANCE.md` §11. Do not maintain a duplicate permissions table here. Runtime validation uses the exact permission keys defined there.

### Foundation data and controlled deletion (F-2; WDS-approved)

Canonical ordered `DataClass` (`internal` < `confidential_client` < `restricted`): `internal`, `confidential_client`, `restricted`. Every Project has `data_classification: DataClass` and every Source has `access_classification: DataClass`; required, never free text. A source cannot be classified below its project classification without explicit authorized reassessment. Effective access is determined by role, project assignment, source ACL, and restricted-content authorization. Classification is not a substitute for authorization.

| Class | Intended content | Access baseline |
|---|---|---|
| `internal` | WDS non-client standards and operational materials | Authenticated authorized WDS role and collection/project access |
| `confidential_client` | Client brief, proposal, estimate, meeting notes, technical system details | Explicit project/collection authorization; no cross-project retrieval by default |
| `restricted` | Highly sensitive financial/security/client records and inadvertently supplied secrets | Explicit restricted-content grant; credentials/secrets excluded from AI indexing; controlled redaction/quarantine |

`AuditTombstone` required: `tombstone_id`, `entity_type`, `entity_id`, `data_class`, `deletion_reason`, `requested_by`, `authorized_by`, `deleted_at`, `deletion_method`, `audit_event_id`; optional `retention_policy_version` (nullable pending D-13); optional `project_id`. `deletion_method` enum: `logical_delete`, `content_purge`, `anonymization`. Both human identities must refer to authenticated authorization records; service execution is separately recorded. Tombstone must not contain deleted content, credentials, or confidential excerpts. Records deleted only logically are not described as physically purged. Never silently delete evidence subject to a legal hold; record block state and audit. Retention durations, legal-hold implementation, and backup purge timings remain pending D-13; do not authorize production deletion schedules based on this contract alone.

### Foundation API DTOs (F-5)

`ProjectCreateRequest` requires `name: nonempty string <= 200`, `data_classification: DataClass`, `client_reference?: string <= 120`, `idempotency_key: UUID`. Server derives `created_by`, `access_boundary_id` and project membership from authenticated actor, not request body. Deny if actor lacks `project.create`. Return project ID, `revision`, and audit event reference. Project creation does not create a WorkflowRun.

`SourceIngestRequest` is multipart binary plus validated metadata: `project_id` from path, `source_type: SourceType`, `title: string <= 255`, `access_classification: DataClass`, `expected_project_revision: int`, `idempotency_key: UUID`; optionally `supersedes_source_id` and `expected_source_revision` for an authorized new version; a supersession requires both. Server derives uploader, size, MIME, hash and storage location. Enforce F-3 upload contract in ARCHITECTURE §13 and project ACL before writing; return source ID, version, parse status and audit event reference. The client may not supply preverified evidence or a trusted storage URI. Upload increments `Project.revision`, including supersessions; all authenticated write operations use optimistic checks. Idempotency keys are scoped to `(actor_id, endpoint, key)` and retained for 24 hours; exact replay returns the stored response, same key with differing payload hash returns HTTP 409 without mutation.

**R3 archived project guard:** `project.archive` MUST return HTTP 409 without mutation while any `WorkflowRun` for that project has `status=queued | running | waiting_human`. Once archived, `run.cancel` remains permitted to an authorized Administrator for any cancellable historical run, while `run.retry` and `run.start` are denied with 409. No unarchive operation is available in Gate 1.

### Foundation version and job fields (F-6–F-10)

`RunStatus = queued | running | waiting_human | blocked_pending_decision | completed | failed | cancelled`. `JobStatus = queued | leased | waiting_human | completed | failed | cancelled`. The canonical run state/status/job mapping and project active-slot predicate live in ARCHITECTURE §7. Only `queued`, `running`, `waiting_human` consume the active-run slot. `blocked_pending_decision` and `failed` are historical/restartable only under §7's administrative checks.


`RunInputSnapshot(snapshot_id, run_id, project_id, source_id, source_version, included_reason, input_revision_hash, created_at)` is immutable; one entry per Source, selecting its latest non-superseded Source version with `scan_status != quarantined` and `parse_status` in `pending | succeeded | partial | unsupported`. `unsupported` items remain explicitly listed for manual review, not fed as extracted text. New uploads never modify an existing snapshot; a running run with modified inputs is marked stale upon completion. Snapshot records are unique by `(run_id, source_id)`.

**R1 first-run rule:** A newly uploaded Source begins with `parse_status=pending`, is eligible for a fresh `RunInputSnapshot` when it is the latest non-superseded version and not quarantined, and MUST be parsed inside that run's `parsing` stage exactly once per `(source_id, source_version, extraction_version)` unless stable extracted segments already exist. Parsing updates the corresponding Source version `parse_status` to `succeeded`, `partial`, `unsupported` or `failed` and records immutable `SourceSegment`s. `unsupported` has no fabricated extracted content; `failed` versions are excluded from later snapshots until an Administrator invokes audited `source.reparse` with a nonempty reason, atomically setting that exact failed Source version to `pending`. An individual parser failure MUST mark only that Source version `failed`; the run MUST continue its other sources and reach `intake_complete` with an itemized failed/unsupported list. Run-level `failed` is reserved for system-level failures (e.g. persistent storage/database failure or exhausted job attempts). A `source.reparse` MUST NOT mutate a prior frozen RunInputSnapshot; the reset version enters only the next eligible Analyst-started run. It does not retry the entire run. A first run containing pending sources MUST NOT yield an empty snapshot when at least one eligible pending source exists. Every run uses its frozen snapshot; later uploads belong only to later runs.

`WorkflowRun`: `run_id`, `project_id`, `state`, `status: RunStatus`, `input_revision_hash`, `revision`, `created_at`, `updated_at`; active runs per project constrained as described in ARCHITECTURE §7. `WorkflowJob` fields and transition table are normative in ARCHITECTURE §7. Every derived record has `derived_run_id`, `input_revision_hash`, `is_stale`, `stale_at?`, `stale_reason?`, and dependency edges. Source and human-editable project records carry integer revision and require expected-revision writes.

### Foundation authorization and dependency entities (B-4, B-10)

`User(user_id, identity_subject, display_name, email, normalized_email, contact_revision: integer, session_epoch: integer, status: pending_contact_approval|pending_activation|active|disabled, created_by_user_id?, contact_approved_by_user_id?, created_at, updated_at)` is the authoritative local identity mapping. Ordinary `user.manage` creates `pending_contact_approval`; standard approved contact moves to `pending_activation`; successful private token activation moves to `active`. Auth and session validation MUST reject `pending_contact_approval`, `pending_activation` and `disabled`, and require a matching `session_epoch` on every session. Credential provisioning and reset are user-owned; Administrators cannot set/see passwords or tokens. Argon2id is required for locally stored password hashes. Setup/recovery users receive a ceremony-backed contact approval, then use the same private activation step.

**Contact approval contracts (P-GATE1-CONTACT-01, B3/B4).** `UserContactApproval(approval_id, user_id, request_type: create|change|appointment, requested_email_normalized, previous_email_normalized?, requested_by_user_id?, approved_by_user_id?, ceremony_id?, proof_ref, status: pending|approved|rejected|cancelled|expired, created_at, expires_at, approved_at?, revision, administrator_appointment: bool = false, appointment_consumed_at?, appointment_role_assignment_id?)` is authoritative. DB CHECK `(ceremony_id IS NULL) = (requested_by_user_id IS NOT NULL)` and CHECK `status <> 'approved' OR ceremony_id IS NOT NULL OR (approved_by_user_id IS NOT NULL AND approved_by_user_id <> requested_by_user_id)`; exactly one human approver or ceremony ID is required on approval. On ceremony-backed approval rows `approved_by_user_id` MUST be NULL, enforced by CHECK `(ceremony_id IS NULL OR approved_by_user_id IS NULL)`; ordinary approved rows MUST have a non-null, distinct human approver.  A BEFORE INSERT/UPDATE **database trigger** for ordinary approvals checks that the human approver is distinct from the `User.created_by_user_id`, holds an active unrevoked Administrator role, and at least two active Administrators exist; it acquires the governance lock for counting. A ceremony-backed approval is allowed only for a signed, authorized ceremony through the dedicated privileged database role, with a matching approved user ID, and does not use a human approver. Every ceremony-backed approved row MUST set `administrator_appointment=true` (including install and recovery) and carry `ceremony_id`; ordinary approvals MUST set it false. `appointment_consumed_at` and `appointment_role_assignment_id` are NULL until a single successful Administrator role assignment consumes that appointment. Appointment markers and consumption fields are immutable to the ordinary application role. A ceremony may use `request_type=appointment` for an existing `active` non-Administrator user, after independently verifying that user and their already-approved current normalized contact; this changes neither `User.status` nor `User.normalized_email`, requires no new contact reservation, and never delivers an activation token. For `request_type=appointment`, `requested_email_normalized` MUST equal the user's current reserved normalized contact, and the `UserContactApproval` status and ceremony authorization are recorded as usual. No ordinary user contact approval may masquerade as a ceremony appointment. A BEFORE UPDATE trigger on `User` rejects `pending_contact_approval → pending_activation` or a change of `normalized_email`/`contact_revision` absent a matching approved, unexpired `UserContactApproval` for that new address and revision, including a unique consumed approval ID. Normal runtime users cannot directly mutate protected state columns. `ContactReservation(reservation_id UUID PRIMARY KEY, normalized_email, user_id, approval_id?, created_at, released_at?)` has a partial unique index on `normalized_email WHERE released_at IS NULL`; released records are retained as history but no longer block reuse. Active reservations include current user contacts (including disabled/pending) and non-expired pending changes; acquire transaction-level locking so active user and pending change never reserve identical normalized addresses. Normalize email with Unicode NFC, trim outer whitespace, convert ASCII-case-insensitive domains/local part to lower-case **before** WDS domain allowlist checking; Gate 1 local parts MUST be ASCII; reject `+` subaddressing and configured denylisted aliases. Mixed-case ASCII input is accepted by normalization. Enforce unique normalized emails across all users including disabled and pending. All ordinary create/change approvals have a 24-hour TTL and injectable-clock behavior. Expired/rejected creation approval keeps `User.status=pending_contact_approval`, sends no token and is auditable; a replacement create approval may be requested, but disable never releases the existing current-contact reservation. Only an audited `user.withdraw` for a NEVER-APPROVED `pending_contact_approval` user atomically marks them disabled, tombstones/clears `User.normalized_email`, releases the current contact reservation, and retains audit/tombstone history; approved or formerly active accounts are ineligible for withdrawal. `UserWithdrawal(withdrawal_id UUID PRIMARY KEY, user_id, actor_user_id, reason, expected_user_revision, created_at, audit_event_id)` records the single authorized never-approved withdrawal and is immutable to application roles. The `user.withdraw` API is Administrator-only with non-empty justification and expected `User` revision; a non-Administrator returns audited 403; eligible-state or revision conflicts return audited 409 with no mutation. On successful withdrawal, cancel all pending create approvals for the user atomically and record the withdrawal before release of the reservation. The service and a database BEFORE UPDATE trigger check `status=pending_contact_approval`, absence of ANY approved contact/ceremony approval history or prior activation, and forbid removal of other users’ contacts. The exceptional clearing of `normalized_email` is permitted only with the matching `UserWithdrawal` row and its linked append-only audit event in the same transaction; the ordinary contact-update guard rejects all other direct clears. A concurrent approval/withdrawal is serialized and one side returns 409. Tombstone stores a non-reversible stable audit identifier, not an active reserved email. Expired or rejected create approval alone MUST NOT release the reserved address. Expired/cancelled/rejected change frees its target reservation and reset hold; active contact is unaffected. Approved contact changes atomically increment `User.contact_revision` and `session_epoch`, invalidate tokens and sessions, consume new reservation, release old reservation and enqueue nonsecret prior-contact notice. Delivery never occurs in the DB transaction; `proof_ref` attests an external WDS verification procedure, not a machine-verifiable mailbox ownership claim.

`AccountActivationToken(token_id, user_id, purpose: activate|reset, token_hash, contact_revision: integer, contact_destination_ref, issued_at, expires_at, consumed_at?, revoked_at?, revocation_reason?, delivery_status: pending|sent|failed, issued_by_actor_id?)` stores hashes only, never token/link plaintext. A partial unique index on `(user_id,purpose)` WHERE `consumed_at IS NULL AND revoked_at IS NULL` permits only one live token regardless of expiration; on new issuance, revoke the old row in the same transaction. Validation checks token hash, unconsumed, unrevoked, expires_at > now, user status and equality with current `contact_revision`; consume atomically. Token TTL is 30 minutes. Contact changes revoke all live tokens and increment `session_epoch` to reject prior sessions. Delivery goes only to independently approved current contact via production-approved private transport or isolated nonproduction test sink; no token or link is exposed to an Administrator. Installation/recovery user contact uses a recorded ceremony-backed approval before private token delivery.

**Token issuance and abuse controls (v0.3.7).** New token issuance atomically revokes the prior live token for `(user_id,purpose)`; successful consumption and contact change invalidate all old tokens by status and `contact_revision`. Approved active account owners may request reset; pending-activation users may request activation resend to the approved contact; authorized approving Administrator may trigger resend but receives no secret. Rate limits are configurable with audited denial and neutral responses: recommended defaults for login are 5 failures/15 minutes per `(account,IP)` and 100 requests/15 minutes per IP, activation/reset/resend 5/15 minutes per user/contact and 100/15 minutes per IP; avoid hard account lockout from unauthenticated attempts. Nonproduction capture sink is allowed solely for tests; reject production startup if configured. Session epoch invalidates prior sessions on reset and contact change. All issuance, revocation, attempts and delivery outcomes are auditable.

**Bootstrap and recovery ceremony (P-GATE1-BOOTSTRAP-02; B1/B2).** `SetupTrustCeremony(ceremony_id, kind: install|recover, owner_approval_ref, signed_authorization_digest, owner_identity_ref, independent_verifier_id, deployment_operator_id, effective_admin_count_at_start, authorized_user_ids, activation_deadline, started_at, completed_at?, closed_at?, status: initiated|completed|closed|failed)` is only created by a restricted owner-signed CLI and dedicated DB role. First installation explicitly creates two distinct verified contacts with `UserContactApproval(ceremony_id)` (exception to ordinary human-approval-count rule); both go to `pending_activation`. `system:bootstrap` creates **only the first** Administrator role assignment once. After that first user privately activates they issue an ordinary audited non-self Administrator role assignment to the independently activated second user, consuming the second contact's ceremony-backed Administrator appointment. The first `system:bootstrap` role assignment is the sole exceptional grant and consumes the first contact's appointment under the controlled install CLI. If an install contact activated before their ordinary role grant but the 24-hour appointment deadline passed, the old appointment is expired and cannot be used: with one active Administrator a NEW signed recovery ceremony must approve a fresh `request_type=appointment` for that existing active contact. While the active Administrator count is below two, ordinary `role.assign` for the Administrator role is allowed ONLY for an `active` target different from the grantor holding an `approved`, unexpired `UserContactApproval` with `ceremony_id` and `administrator_appointment=true`, `appointment_consumed_at IS NULL`, and no previous Administrator role assignment issued against that approval. Eligible targets include new privately activated ceremony contacts and existing active staff with an independently verified `request_type=appointment` from a fresh owner-signed recovery ceremony; no unapproved staff promotion is allowed below two. On a successful grant, the RoleAssignment stores `appointment_approval_id` and atomically sets `appointment_consumed_at` and `appointment_role_assignment_id` under the governance lock; reuse returns audited HTTP 409. A `BEFORE INSERT` database trigger on `RoleAssignment` checks active count, target/grantor distinction, approved ceremony and appointment marker, unexpired deadline, no earlier consumption or matching role assignment, and validates the same transaction consumes the approval. The trigger also rejects insertion of an Administrator role for a below-two target without a valid appointment; client-supplied approval IDs alone never bypass authorization. Use the ordinary grantor identity and preserve R2 no-self-assignment, under the same serialized governance lock. The install marker is immutable and closed after contact setup; readiness requires two activated users with unrevoked Administrator grants. Recovery via ceremony is allowed only when exactly one active Administrator exists and **effective Administrator coverage** is below two; remaining Administrator grants Administrator role to the privately activated replacement via ordinary non-self `role.assign`. Effective coverage counts distinct active users holding unrevoked Administrator grants PLUS ceremony-approved unexpired pending replacements reserved for Administrator appointment (pending activation or awaiting ordinary role grant), with each user counted at most once. Reject another ceremony while a replacement reservation is valid, even if active count stays one. ALL ceremony-approved installation contacts AND recovery replacements have a 24-hour activation deadline from contact approval. On missed deadline, expire that ceremony contact approval and invalidate tokens and prospective coverage, with no late activation. After missed installation contact #2 activation and an active #1, use one-Administrator recovery. If installation contact #1 misses activation, zero active Administrators remains: no in-system recovery grant is possible and the WDS-confirmed owner-authorized offline restore/reinstall policy P-GATE1-ZERO-ADMIN-RECOVERY-03 applies. A recovery replacement also expires without full activation/role grant by the deadline; the slot is released and a new owner-signed recovery may be requested. Normal ceremony recovery with zero active Administrators MUST be refused (no ordinary human grantor): owner-approved offline restore/reinstallation is required outside the runtime and is **CONFIRMED by WDS under P-GATE1-ZERO-ADMIN-RECOVERY-03 (2026-10-16)**; the offline action MUST have signed owner authorization, authorized operator identity, an approved operational runbook and auditable execution evidence, none of which authorizes an in-system exception. A single install ceremony permanently closes, and recovery never reopens installation. Owner key, independent verifier, immutable audit, dedicated DB writer and serialized database triggers enforce ceremony caps; no public API accepts caller-supplied ceremony actor IDs. Database operators remain a declared residual trust boundary.

`OutboxNotice(notice_id, purpose: prior_contact_change|delivery_failure_alert, user_id, old_contact_ref?, payload_redacted, status: queued|leased|sent|dead_letter, attempt_count, available_at, created_at, delivered_at?, last_error_class?, lease_owner?, lease_expires_at?)` is inserted in the **same transaction** as the approved contact update and token/session revocation. Workers acquire notices with row-level lease (`FOR UPDATE SKIP LOCKED`) using the F-6 lease TTL 120 seconds and renewal every 30 seconds; expired leases are reclaimed, delivery is idempotent by notice ID, and retry/dead-letter policy is versioned configuration. Out-of-transaction transport failure never undoes the contact change. Terminal delivery failure creates an audited *in-app* operational alert, even when mail is down, to active Administrators; notice content never contains secrets.



`RoleAssignment(assignment_id, user_id, role: Analyst|TechnicalReviewer|Approver|Administrator, assigned_by, appointment_approval_id?, created_at, revoked_at?)`; `ProjectMembership(membership_id, project_id, user_id, assigned_by, created_at, revoked_at?)`; `ProjectAccessGrant(grant_id, project_id, user_id, permitted_actions, granted_by, created_at, revoked_at?)` with DB CHECK (`granted_by != user_id`); `RestrictedContentGrant(grant_id, resource_type: project|source, resource_id, user_id, granted_by, reason, created_at, expires_at?, revoked_at?)` with DB CHECK (`granted_by != user_id`). Only Administrator may manage role/membership/grant records; no grant can bypass a role-specific action denial. Every issue, revoke and expiry is logged and checked at read-time. Admin must obtain an explicitly separate content grant to read client bytes, with grant creation and use audited. Gate 1 is a single WDS organization; multi-org isolation is a future contract, so no `organization_id` is stored on the tombstone.

**R2 no self-assignment:** For `RoleAssignment` and `ProjectMembership`, the default DB CHECK and application-service invariant is `assigned_by != user_id` whenever `assigned_by` is a human user ID. A human Administrator attempting to assign their own role or membership is rejected with HTTP 403 and an audit event, even if they have management permission. Only two system-principal exceptions exist: the single FIRST Administrator role assignment by `system:bootstrap` during controlled installation (audited with reason, immutable bootstrap marker and once-only safeguard), and an Analyst project creator's initial automatic membership created by `system:project_create` as part of the same authorized `project.create` transaction (audited, limited to that project and creator). Neither exception permits arbitrary role assignment, self-granted content access, or subsequent self-membership. Database constraints MUST reject a human self-assignment and accept only registered system-principal exceptions with validated operation context; do not trust caller-supplied `assigned_by`. The only authorized system-principal values are the two exact names above. Grant-table no-self-grant checks remain in force.

**Session storage contract (S6).** `Session(session_id, user_id, session_epoch_at_issue, issued_at, expires_at, revoked_at?, last_seen_at?)` is server-side and every authenticated request validates `User.status=active`, absence of revocation, expiry and equality of `session_epoch_at_issue` with current `User.session_epoch`. Session row revocation or user epoch increment immediately invalidates future use. No client-side session claim is authoritative without comparison.

`DependencyEdge(edge_id, project_id, upstream_type, upstream_id, upstream_revision, downstream_type, downstream_id, downstream_revision, created_at)` supports immutable run derivation graphs; no cycles accepted. Gate 1 derived entities are `SourceSegment` (from Source version) and `WorkflowRun` snapshots (from Project/Source revisions); all other derived types are later phase. Invalidation is transitive, idempotent and audited.

**Atomic source parse failure (v0.3.7):** Parsing one Source version is atomic: failure rolls back **all** newly produced `SourceSegment` rows for that version/extraction attempt; it writes only a version-scoped failed parse status and an auditable error record. No partial segment set is committed for a failed parse. Existing stable segment sets remain immutable and cannot be overwritten by reparsing. A parse is `partial` only when a parser intentionally completes with a valid, committed segment set while explicitly identifying bounded unextractable regions. Any unexpected exception, corrupt document, or interrupted extraction is `failed` and rolls back ALL new segments for that source-version/extraction attempt; zero extractable text with a valid image-only document is `unsupported`, not `failed`. Partial outputs MUST NOT contain silently truncated records.

`SourceReparseRequest(source_id, source_version, expected_source_revision, reason, idempotency_key)` is an Administrator-only `source.reparse` command. Only `parse_status=failed`, non-superseded, non-quarantined versions of active projects are eligible; a nonempty reason and audit record are required. A source version is transitioned atomically to `pending` with revision increment; earlier source segments and run snapshots are immutable, and new processing occurs in the next Analyst-started run. An invalid state or stale revision returns HTTP 409 without mutation; lack of permission returns 403 and is audited. Parsing does not start inside `source.reparse`.

`RunStartRequest(project_id, expected_project_revision, idempotency_key)` and `RunControlRequest(run_id, operation: cancel|retry|resume, expected_run_revision, reason, idempotency_key)` use permission keys `run.start`, `run.cancel`, `run.retry`, `run.resume`. Runtime enforces ARCHITECTURE §7 run-slot rule; a parked run's snapshot remains immutable. Gate 1 no deletion or purging API exists.

## 4. Core entity contracts

The fields below define the logical contract. Database-specific normalization may differ but must preserve the semantics.

### 4.1 Project

Required: `project_id`, `name`, `created_at`, `created_by`, `status`, `access_boundary_id`, `revision: int` (initially 1, increment on metadata edits, uploads, source versioning, archival and access-affecting project mutations).
Optional: `client_reference`, `business_context`, `platforms` (one or more identifiers), `application_types`, `technologies`, `specialist_categories`, `service_pattern_ids`, `constraints`, `updated_at`.
`status`: `active`, `archived`, `deleted_pending_retention`. Gate 1 supports only `active` and `archived`; archived projects reject all edits, uploads, new runs and source version mutations with HTTP 409, and cannot be unarchived in Gate 1. `data_classification: DataClass` is **required** (F-2), not optional.
Do not put unnecessary personal data in project metadata.

### 4.2 Source and source segment

`Source` required fields: `source_id`, `project_id`, `source_type`, `title`, `source_trust`, `content_hash`, `ingested_at`, `ingested_by`, `parse_status`, `version`.
Optional: `uri_or_storage_key`, `publisher`, `published_at`, `retrieved_at`, `mime_type`, `file_size_bytes`, `supersedes_source_id`, `parse_error`.
`access_classification: DataClass` is **required** on every Source (F-2). `parse_status`: `pending`, `succeeded`, `partial`, `failed`, `unsupported`. `scan_status` required: `not_scanned | clean | quarantined`; `unprocessed_attachment` is an array of records `(filename, declared_mime_type, declared_size_bytes, disposition=unprocessed)` from EML metadata, never ingested Source bytes or segments.

`SourceSegment` required fields: `segment_id`, `source_id`, `source_version`, `locator_type`, `locator`, `text_excerpt_hash`.
Optional typed locator fields: `excerpt`, `page_number`, `heading_path`, `paragraph_index`, `line_start`, `line_end`, `start_offset`, `end_offset`, `message_id`, `eml_part`, `timestamp_start`, `timestamp_end`; `extraction_version` is required. `LocatorType = pdf_page | docx_paragraph | md_heading_paragraph | txt_line_range | eml_part`. PDF segments are per page (or page-contained text region), DOCX per paragraph, MD per heading+paragraph, TXT per line range, EML per subject/body part; other headers are provenance metadata only and never form content segments. For each type, its relevant locator fields are required and validated.
Segments MUST be generated only once per `(source_id, source_version, extraction_version)` and reused across subsequent runs. Enforce unique `(source_id, source_version, extraction_version, locator_type, locator)` and never remint `segment_id` for the same segment key; `derived_run_id` stores the first producing run, not the most recent consuming run. Locators must be stable within the source version. Canonical `locator` uniqueness uses RFC 8785 JSON of type-specific non-null locator fields and `locator_type`; irrelevant and null fields are omitted. Preserve the original file even if extracted text changes.

### 4.3 Requirement

Required fields:
- `requirement_id`
- `project_id`
- `origin: RequirementOrigin`
- `original_wording`
- `normalized_statement`
- `requirement_type: RequirementType`
- `status: RequirementStatus`
- `materiality: Materiality` (required; `unassessed` is blocking in gates)
- `source_refs: SourceReference[]` (minimum one for client-derived requirements)
- `evidence_status: EvidenceStatus`
- `confidence: ConfidenceBand`
- `created_at`, `created_by`, `revision`

Optional:
- `priority: Priority`
- `business_impact` (must be evidence-supported)
- `acceptance_criteria: AcceptanceCriterion[]`
- `assumption_refs`, `evidence_refs`
- `dependency_ids`, `conflict_ids`, `related_requirement_ids`
- `clarification_question_ids`
- `assigned_capabilities` (registry IDs; one or more may apply)
- `platform_refs` (zero or more platform/product identifiers; empty for platform-agnostic work)
- `application_types` (for example `standalone_application`, `middleware_application`, `commerce_customization`)
- `technology_candidates` (candidate technologies with rationale/evidence; not mandatory implementation choices)
- `specialist_category_ids` (selected logical Layer 2 categories; may be multiple)
- `service_pattern_ids` (stable `SVC-...` IDs from `SERVICE_CATALOG.yaml`)
- `specialist_findings` (references to validated specialist outputs; do not inline unsupported claims)
- `candidate_solution_ids`
- `security_considerations`, `privacy_considerations`, `performance_considerations`, `operational_considerations`
- `estimate_refs`, `scope_item_ids`
- `derived_from_requirement_ids`, `supersedes_requirement_id`
- `last_updated_at`, `last_updated_by`

`SourceReference`: required `source_id`, `source_version`, `segment_id` (canonical persisted locator). Optional auxiliary navigation: `page`, `heading_path`, `message_id`, `timestamp`, `start_offset`, `end_offset`, `supporting_quote`, `relation` (`supports`, `contradicts`, `context`). Auxiliary locators MUST NOT replace `segment_id`. Validate that segment belongs to the specified source version and project.

`AcceptanceCriterion`: required `criterion_id`, `statement`, `verification_method`; optional `measurable_target`, `source_refs`, `status`. Do not invent a numeric target. If no measurable target is supplied, state that acceptance wording needs client agreement.

### 4.4 Evidence and claim

`EvidenceRecord` required: `evidence_id`, `project_id`, `source_id`, `source_version`, `evidence_status`, `retrieved_or_checked_at`, `relevance_summary`.
Optional: `locator`, `excerpt`, `publisher`, `source_date`, `content_hash`, `applies_to_platform_version`, `limitations`, `checked_by`, `related_claim_ids`.

`Claim` required: `claim_id`, `project_id`, `claim_text`, `claim_type`, `evidence_status`, `feasibility_status`, `materiality`, `subject_refs`, `created_at`.
Optional: `evidence_refs`, `applies_to_context`, `verification_task`, `owner`, `confidence`, `contradiction_refs`, `verification_actor_id`, `verification_at`, `source_version_checked`, `materiality_decision_id`.
`claim_type`: `platform_capability`, `api_behavior`, `security`, `performance`, `cost`, `implementation`, `estimate`, `business`, `other`.
Material technical claims require evidence references or an explicit unverified state and verification task.

### 4.5 Clarification question

Required: `question_id`, `project_id`, `question_text`, `reason`, `status`, `created_at`.
Optional: `related_requirement_ids`, `impact_if_unanswered`, `suggested_answer_options`, `asked_to`, `answer`, `answered_at`, `answered_by`, `waiver_reason`, `waived_by`.
A waived question requires an authorized human and rationale. Waiving a question does not automatically make a claim verified.

### 4.6 Candidate solution

Required: `solution_id`, `project_id`, `summary`, `approach_type`, `feasibility_status`, `evidence_status`, `related_requirement_ids`, `created_at`.
Optional: `advantages`, `limitations`, `prerequisites`, `dependency_ids`, `risks`, `alternatives`, `evidence_refs`, `verification_tasks`, `recommendation_rationale`, `claim_ids`.
`approach_type`: `native_platform`, `platform_extension`, `third_party_app`, `api_integration`, `middleware`, `custom_backend`, `rule_based_automation`, `ai_ml`, `manual_process`, `other`.
A solution is a candidate until review and human acceptance.

### 4.7 Scope item

Required: `scope_item_id`, `project_id`, `title`, `description`, `status`, `commitment`, `materiality`, `requirement_ids`, `acceptance_criteria`, `created_at`, `revision`.
`requirement_ids` must be non-empty for committed scope. Optional recommendations without source requirements must be clearly marked optional.
Optional: `deliverables`, `dependencies`, `assumption_ids`, `exclusion_ids`, `risk_ids`, `solution_ids`, `estimate_id`, `evidence_refs`, `owner_role`, `out_of_scope_notes`, `test_strategy`, `review_finding_ids`.
A scope item cannot be `accepted_for_draft` if it has unresolved blocking findings or critical unverified claims.

### 4.8 Estimate

Required: `estimate_id`, `project_id`, `unit: EstimateUnit`, `status: EstimateStatus`, `basis`, `assumptions`, `uncertainty`, `created_at`.
Optional: `low`, `most_likely`, `high`, `point_value`, `scope_item_ids`, `dependencies`, `exclusions`, `estimator_id`, `reviewer_id`, `confidence`.
Rules: values must be non-negative; if a three-point range is used, `low <= most_likely <= high`; the unit must be explicit. Do not mix units within one estimate. `unknown` unit cannot be approval-ready.

### 4.9 Assumption, risk, exclusion, and relation

`Assumption`: `project_id`, `assumption_id`, `statement`, `rationale`, `status`, `impact_if_false`, `created_at`; optional `owner_to_confirm`, `related_requirement_ids`, `related_scope_item_ids`, `evidence_refs`, `confirmed_by`, `confirmed_at`. Status: `proposed`, `needs_confirmation`, `confirmed`, `rejected`, `superseded`.

`Risk`: `project_id`, `risk_id`, `description`, `status`, `mitigation`, `created_at`; optional `likelihood`, `impact`, `owner`, `related_requirement_ids`, `related_scope_item_ids`, `evidence_refs`. Status: `open`, `mitigating`, `accepted`, `closed`.

`Exclusion`: `project_id`, `exclusion_id`, `statement`, `rationale`, `related_scope_item_ids`, `created_at`; optional `confirmed_by`, `confirmed_at`.

`RequirementRelation`: `from_requirement_id`, `to_requirement_id`, `relation_type`, `created_at`. Relation types: `depends_on`, `conflicts_with`, `duplicates_candidate`, `refines`, `derived_from`, `supersedes`, `related_to`. Conflicts must not be automatically erased by choosing one record.

### 4.10 Review, finding, decision, artifact, and audit event

`Review`: `review_id`, `project_id`, `artifact_version`, `reviewer_type`, `outcome`, `checklist_version`, `created_at`; optional `reviewer_id`, `finding_ids`, `summary`, `model_config_ref`.

`ReviewFinding`: `project_id`, `finding_id`, `review_id`, `severity`, `status`, `category`, `description`, `evidence_refs`, `affected_requirement_ids`, `affected_scope_item_ids`, `required_action`, `created_at`; optional `resolved_at`, `resolution_note`, `accepted_risk_decision_id`.

`HumanDecision`: `decision_id`, `project_id`, `artifact_version`, `decision`, `actor_id`, `actor_role`, `rationale`, `timestamp`; optional `finding_dispositions`, `artifact_hash`, `supersedes_decision_id`. Actor authorization is validated outside the LLM.

`SOWArtifactVersion`: `artifact_id`, `project_id`, `version`, `content_hash`, `status`, `created_at`, `created_by`, `submitted_by`, `prepared_by`, `traceability_snapshot`; optional `review_id`, `decision_id`, `export_uri`. `submitted_by` and `prepared_by` are accountable human IDs, not service principals; no final approver may match either. Status: `draft`, `in_review`, `changes_required`, `internally_approved`, `rejected`, `superseded`, `withdrawn`.

`AuditEvent`: `event_id`, `project_id`, `actor_type`, `actor_id_or_service`, `event_type`, `timestamp`, `correlation_id`, `record_refs`; optional `before_hash`, `after_hash`, `configuration_versions`, `outcome`, `error_class`, `redacted_details`. Do not store secrets or hidden chain-of-thought.

### 4.3.1 Specialist routing metadata

Routing metadata is additive and must not alter `RequirementOrigin`, source provenance, or lifecycle semantics. Use stable registry IDs and catalog service IDs. A requirement may reference multiple platforms, application types, technologies, specialist categories, service patterns, and dependency IDs. Empty platform references are valid for platform-agnostic standalone applications. `selected`, `not_selected`, `clarification_needed`, `unsupported`, and `unavailable` are routing outcomes, not requirement lifecycle states. Store selection rationale, trigger signals, registry/catalog versions, and specialist output validation status in the run/routing record.

Specialist output contract: `requirement_ids`, `specialist_category_id`, `service_pattern_ids`, `findings`, `claims`, `risks`, `dependencies`, `clarification_questions`, `evidence_refs`, `status`, `validation_errors`, `registry_version`, `catalog_version`. Material claims must retain platform/version context and `EvidenceStatus`; outputs are proposals until validated.

## 5. Lifecycle transitions

### Requirement lifecycle
- `captured -> normalized | needs_clarification | blocked`
- `normalized -> needs_clarification | under_analysis | rejected`
- `needs_clarification -> normalized | under_analysis | blocked`
- `under_analysis -> solution_proposed | needs_clarification | blocked`
- `solution_proposed -> verified | needs_clarification | blocked`
- `verified -> accepted_for_scope | deferred | rejected | blocked`
- `accepted_for_scope -> under_analysis | superseded` (reopen/change creates an audited revision)
- `deferred -> under_analysis | rejected | superseded`
- `blocked -> captured | normalized | needs_clarification | under_analysis`
- `rejected -> superseded` only if replaced by a new revision/requirement
- `superseded` is terminal

Transitions require a recorded actor, timestamp, and reason. Only authorized humans may accept/reject requirements for scope. The application may propose transitions but cannot bypass permissions.

### Review and artifact lifecycle
- Review outcomes: `blocked`, `changes_required`, `pass_with_conditions`, `pass`.
- Artifact statuses: `draft -> in_review -> changes_required -> in_review`; `in_review -> internally_approved` only after required checks and human decision; rejected/superseded/withdrawn statuses are terminal for that version.
- `pass_with_conditions` is not equivalent to approval if any release gate remains open.
- A changed artifact creates a new version and requires revalidation. Material changes require re-review.

## 6. Validation rules

1. IDs are unique and immutable.
2. Every client-derived requirement has at least one valid source reference.
3. Every source reference points to an existing source version and valid locator where available.
4. Original wording cannot be overwritten during normalization.
5. Origin and recommendation/client-intent distinctions are mandatory.
6. Every scope item has requirement mappings unless clearly marked optional and non-committal.
7. Every material claim has evidence or `unverified` plus a verification task.
8. `conflicting` evidence/feasibility requires conflict references and blocks affected scope approval.
9. Estimate ranges are ordered, non-negative, and use one unit.
10. A state transition must be allowed and authorized.
11. Project-bound records must share the same project boundary; cross-project references are rejected by default.
12. Accepted/approved states require required review and audit records.
13. Source content is never interpreted as configuration or policy.
14. Null/unknown must not be converted to a false/empty value that implies confirmation.

## 7. Representative examples

### Example A — Clear requirement

```yaml
requirement_id: REQ-EX-001
project_id: PRJ-EXAMPLE

original_wording: "When an order is placed, send its order number and status to our ERP."
normalized_statement: "Transmit the store order identifier and agreed order status fields to the client's ERP after order creation."
requirement_type: integration

clarification_question_ids: [Q-EX-001]
```

The high-level request is clear, but trigger semantics, field mapping, ERP API, retries, and failure handling still require investigation.

```yaml
requirement_id: REQ-EX-002
```

### Example C — Potential technical dependency

```yaml
requirement_id: REQ-EX-003
project_id: PRJ-EXAMPLE
origin: client_explicit
```

### Example D — Unverified technical claim (not a fabricated requirement)

### Example E — Conflicting requirements
```yaml
requirement_id: REQ-EX-006
project_id: PRJ-EXAMPLE
origin: client_explicit
```

## 8. Pydantic implementation notes

Implement enums as Python `Enum` classes and entities as Pydantic models with strict validation. Use timezone-aware timestamps, bounded strings, validated IDs, explicit nullable fields, and `extra="forbid"` for model-generated payloads. Separate input DTOs from persisted entities where server-owned fields (IDs, actor, timestamps, authorization) must not be model-controlled. Cross-record constraints belong in application/domain validators and database constraints, not solely in LLM prompts.

The YAML snippets above are illustrative schema examples; `SERVICE_CATALOG.yaml` and `AGENT_REGISTRY.yaml` are the machine-readable configuration files for their respective domains.

## 9. Later-phase contracts and unresolved specifications

The addendum below is normative for approved D-02..D-09 rules; where older examples or lifecycle prose disagree, resolve the inconsistency before approving the affected phase and cite the resolution in the version changelog and treat that section as pending alignment (do not silently guess). This is a **working review draft**, not a completed contract.

### 9.1 Enums and required fields

- `Materiality = material | non_material | unassessed`. Required on Requirement, Claim, ScopeItem; default `unassessed` and **gate as material** until deterministic assessment. `materiality_decision_id` required for human downgrade.
- `ScopeCommitment = committed | optional_recommendation | excluded`. Required on ScopeItem. A committed item MUST have linked requirements with `client_explicit` origin or a version-matched, explicit reviewer-accepted inference; MUST NOT have unverified/conflicting material supporting claims, stale dependencies or unresolved critical findings.
- `CriticalityAssessment = critical | non_critical | unassessed`. Required for criticality-relevant findings/claims; `unassessed` blocks any gate demanding safe disposition. Trigger predicates for security, privacy, data integrity, payments, access control and fundamental feasibility are required as a versioned deterministic policy; their field-level conditions remain **OPEN**.
- `Claim.subject_refs` is an always-required nonempty list of typed `{subject_type: requirement|candidate_solution|scope_item, subject_id, project_id}` for ALL claims. Every reference must remain inside the same project; shared knowledge is evidence input, not a cross-project claim link.
- `CandidateSolution.claim_ids` are zero or more same-project Claim IDs; a solution relied on for committed scope requires the material supporting claim links needed to validate it.
- Every project-scoped `Assumption`, `Risk`, `Exclusion`, `ReviewFinding`, `Claim`, decision, scope, task and estimate carries `project_id` and access boundary checks.
- `Requirement` retains `origin` permanently; record reviewer acceptance separately (decision ID, actor, role, input revision, timestamp, reason and evidence refs). Do not equate origin with approval.
- `RequirementAcceptanceEvent` requires `event_id`, `project_id`, `requirement_id`, `requirement_revision`, `action`, `actor_id`, `actor_role`, `timestamp`, `before_status`, `after_status`, optional `bulk_operation_id`, `reason`, `evidence_refs`. A bulk operation MUST emit one event per acted-on requirement.
- `RiskAcceptance` requires `risk_acceptance_id`, `project_id`, `finding_id`, `accepted_by`, `role`, `risk_owner`, `rationale`, `mitigation`, `review_due_at`, `created_at`; validator forbids it for critical findings.
- `FindingReclassification` requires `decision_id`, `project_id`, `finding_id`, `old_severity`, `new_severity`, `supporting_evidence_refs`, `rationale`, `actor_id`, `timestamp`. It is independent from waiver/accept-risk and may not be proposed as an executable action by an LLM.

### 9.2 Estimation work breakdown (D-04)

`Task`: required `task_id`, `project_id`, `scope_item_id`, `title`, `discipline`, `unit=hours`, `low_hours`, `likely_hours`, `high_hours`, `estimation_basis_refs`, `assumption_ids`, `estimate_status`, `created_at`; optional `service_pattern_id`, `reviewer_id`, `approved_at`, `revision`. Discipline is one of `business_analysis`, `ui_ux`, `frontend`, `backend`, `qa`, `project_management`, `devops_deployment`. Enforce `0 <= low_hours <= likely_hours <= high_hours`. Do not populate invented numeric estimates when neither authorized historical estimate nor approved reference range nor human estimator input exists. Approved status requires a recorded authorized WDS human decision. Sum task ranges deterministically, with explicitly documented aggregation assumptions; do not use implied project duration.

### 9.3 Knowledge permissions and evidence (D-02, D-03)

`KnowledgeCollection`: `collection_id`, `category`, `owner`, `access_policy_id`, `created_at`. Allowed initial categories: `wds_technical_standards`, `approved_service_patterns`, `historical_client_sows_proposals`, `historical_development_estimates`, `internal_technical_documentation`.

`KnowledgeDocument`: `knowledge_document_id`, `collection_id`, `source_identity`, `classification`, `permission_record_id`, `redaction_status`, `ingestion_status`, `publisher`, `created_at`; project-scoped client material additionally requires `source_project_id` and an explicit authorized sharing policy, otherwise retrieval must remain project-local. `KnowledgeDocumentVersion`: `version_id`, `knowledge_document_id`, `content_hash`, `retrieved_at`, `source_version`, `access_review_at`, `superseded_by`; `Chunk`: `chunk_id`, `version_id`, `ordinal`, `content_hash`, `locator`, `text_ref`, `acl_ref`.

Hybrid retrieval means ACL-filtered internal retrieval FIRST, then allowlisted live, read-only official sources for missing/stale/version-sensitive questions; live results MUST preserve URL, timestamp, source version and excerpt locator. The exact source allowlist, freshness maxima and ranking/retrieval parameters remain **OPEN**. Shared documents do not use fabricated `Source.project_id`: model global knowledge independently, and attach evidence within the allowed project context.

### 9.4 Scope acceptance and enforcement

- Acceptance of AI-inferred requirement is an explicit authenticated user action against an exact revision, not an LLM suggestion or implicit SOW approval (D-07).
- Bulk acceptance is permitted only after deterministic eligible-item screening. Blocked, conflicting, stale and unresolved items must be excluded and individually handled. Screening result includes per-item accepted/skipped/ineligible with reason; action-level role permissions and full status predicates remain **OPEN** (D-08).
- Critical findings cannot use `accepted_risk`; approval Gate E and F reject them until genuinely resolved or explicitly evidence-reclassified. Reclassification cannot be used to bypass evidence requirements (D-09).
- `ScopeItem.status` is a workflow status, distinct from `ScopeItem.commitment`. Never infer commitment from `accepted_for_draft` alone.
